# Waitlist COLA: a record-blind NBA draft order with no tanking reward

Paper, simulation harness, and analysis code for our MIT Sloan Sports Analytics
Conference (SSAC27) submission, in the Basketball track.

Carry-Over Lottery Allocation (COLA) gives every team a waiting number that
rises each season it misses the playoffs and falls when it succeeds, and sets
draft priority from that number, so one bad season barely moves a team. This
work formalizes COLA as a space of seven design settings, evaluates nine draft
rules inside a full basketball simulator, and identifies the simplest
configuration that removes the reward for losing while still directing the
earliest picks to the longest-waiting teams.

## Reproducing the numbers

The mechanisms are configurations of the lottery code inside ZenGM
Basketball-GM, an open-source basketball simulator that plays out every game
from generated rosters and contracts under automated general managers. League
generation and every draw are seeded per replicate, so a given configuration and
seed reproduce a run exactly.

Requirements: Node.js 18 or later. The Overleaf sync drops the executable bit
on the shell scripts, so after cloning run `chmod +x testbed/harness/*.sh`
before any of the runners below.

From `testbed/harness`, each script prints one reported result:

    node gap_decomposition.js     where the reward for losing comes from (Table 1)
    node paper_tables.js          the two-ranking comparison and help gradients
    node tank_counterfactual.js   picks bought by losing, paired counterfactual
    node tank_crosscheck.js       independent Monte Carlo check of the above
    node pool_swap.js --validate  pool manipulation, plus model-vs-engine checks
    node tank_engine.js           the behavioral tanking arm
    node metric_screen.js         candidate priority metrics, runs on committed data
    node frontier_analysis.js     the four-criteria comparison on the 25-season run
    node t321_adopted_check.js runs/frontier/t321.json
                                  verifies the adopted 3-2-1 arm against its rules

`metric_screen.js` and `frontier_analysis.js` work on a fresh clone with no
setup, because their inputs are committed: one reference run
(`testbed/harness/runs/ref/nba.json`) and the nine mechanism files of the
25-season run (`testbed/harness/runs/frontier/*.json`, 30 leagues each on
shared seeds). The other scripts read run outputs under
`testbed/harness/runs/`, which are regenerated by the runners in the same
directory (`e14_run.sh`, `ref_run.sh`, `tank_run.sh`, `frontier_run.sh`).
Those runs take several hours; `frontier_watchdog.sh` keeps the long one
within memory and disk on its own.
